<objective>
Production `POST /api/custom-planes` returns 400 `invalid_image` for every image
submission. The `catch` around `moderate()` logs nothing, so the real error has
never been seen. This plan makes the failure observable, stops blaming the image
for failures the image did not cause, and removes two ways the moderation
pipeline can fail permanently.

Purpose: recover the actual production error, and harden the two init paths that
can turn a single transient failure into a permanent outage.
Output: logged and correctly attributed moderation failures; a model cache that
retries after a failed init; a CPU fallback when the WASM backend is unavailable.
</objective>

  <name>Task 1: Make model init survivable — CPU fallback and no cached rejection</name>
  <files>planechaser/src/lib/moderation/image.ts, planechaser/src/lib/moderation/image.test.ts</files>
  <action>
Two independent single-point-of-failure fixes in `image.ts`, plus coverage.

FIX-04, `initBackend` (currently lines 27-40): keep `setWasmPaths` exactly as it
is, then attempt `tf.setBackend('wasm')` defensively. `setBackend` resolves to a
boolean and signals failure by resolving `false` on some paths and by rejecting
on others, so handle both: wrap the await in try/catch, treat a thrown error and
a `false` result identically, and on either outcome log a `console.warn` naming
the failure and the fallback, then `await tf.setBackend('cpu')`. Call
`await tf.ready()` once at the end, after whichever backend was selected.
`@tensorflow/tfjs` registers the CPU backend by default in Node, so no new
dependency is required. Do not swallow a CPU failure — if CPU also fails, let it
throw; task 2 tags it and task 3 logs it.

Extend the existing comment block rather than replacing it. The measured numbers
already in that comment (~330ms load / ~95ms classify on WASM versus ~1750ms /
~1400ms on CPU, identical scores) are the justification for the fallback: with
`maxDuration = 30` on the route, CPU is a slow success rather than a hard
failure. Say that; do not restate what the code does.

FIX-03, `getModel` (currently lines 42-47): `modelPromise ??=` caches a rejected
promise, so one failed cold start poisons every later request in that lambda
instance for its lifetime — which matches the reported symptom of four
consecutive identical failures. Replace the `??=` with an explicit
create-and-register path: assign the new promise to a local first, attach a
rejection handler that clears `modelPromise` only if it still holds that same
local (so a retry already in flight is not nulled out by a late handler from the
previous attempt), then store the local in `modelPromise` and return it. The
handler exists purely to reset the cache — it must not alter what callers
observe, and callers must still receive the rejection. Attaching it also means
the rejection is handled, so no unhandled-rejection warning is produced.

Comment the reset with the reason (a rejected promise is otherwise cached for
the life of the instance), not the mechanism.

Tests in `image.test.ts` — extend, do not restructure. Keep the existing
`syntheticJpeg` helper, the existing three tests, and the file's framing comment.
Add two tests using the real model, real sharp, no mocks:
  1. After a successful `scoreImage`, assert `tf.getBackend()` is one of `'wasm'`
     or `'cpu'` — this proves backend selection produced a usable backend on
     whichever path was taken, without pinning the result to the machine running
     the suite. Import `* as tf from '@tensorflow/tfjs'` for this.
  2. A failed decode must not poison the module: assert `scoreImage(Buffer.from('not an image'))`
     rejects, then assert a following `scoreImage(await syntheticJpeg())` still
     returns five classes. Add a short comment stating plainly that this covers
     failure recovery at the classify stage, and that the init-rejection reset
     cannot be exercised without faking the backend, which this suite
     deliberately does not do.
Use the same `60_000` timeout as the existing tests.

FIX-02 (library half). `moderate()` runs `scanText` and `scanImage` under one
`Promise.all`, so a caller catching its rejection cannot tell which scan threw.
That is why a text-scan failure currently reports a bad image.

In `index.ts`, export a `ModerationScanError` class extending `Error` with a
readonly `stage: 'text' | 'image'` field. Pass the original error through as the
standard `cause` (the `{ cause }` ErrorOptions form on `super`) so no diagnostic
detail is lost — task 3's log depends on that. Give it a `message` that names the
stage and a `name` of `'ModerationScanError'`.

Rewrite the `Promise.all` so each half is wrapped and rethrows as
`ModerationScanError` with its own stage. Four details that matter:
  - `scanText` is synchronous and is currently invoked as the argument to
    `Promise.resolve(...)`, so a throw from it escapes `moderate` before the
    `Promise.all` is constructed. The wrapper has to be a function invoked inside
    the promise chain, not a bare call.
  - Preserve the concurrency. Both promises must still be passed to a single
    `Promise.all` so both have handlers attached and neither produces an
    unhandled rejection when the other rejects first. Do not serialise the awaits.
  - Preserve the existing behaviour that no image scan runs when `imageBytes` is
    null, and that `scores` is then null.
  - If the caught value is already a `ModerationScanError`, rethrow it rather
    than double-wrapping.

Keep the existing comment explaining why the two scans run concurrently, and add
one explaining why the origin has to be distinguishable (the route's user-facing
message differs, and blaming the image for a text-scan failure is what shipped).

Coverage — new file `planechaser/src/lib/moderation/index.test.ts`, first line
`// @vitest-environment node`. Real pipeline, no mocked model client:
  1. `moderate` with `imageBytes` set to `Buffer.from('not an image')` and clean
     text fields rejects with a `ModerationScanError` whose `stage` is `'image'`
     and whose `cause` is defined. This is a genuine sharp decode failure, not a
     simulated one.
  2. `moderate` with `imageBytes: null` and clean text fields resolves with
     `imageFlagged: false`, `textFields: []`, and `scores: null` — the text-only
     path must not be able to produce an image verdict.
  3. `moderate` with `imageBytes: null` and profanity in one field returns that
     field in `textFields` and still `scores: null`. Reuse a term the existing
     `text.test.ts` already treats as a true positive.
Add a short header comment noting that the image case runs the real decode path,
so the tag is proven against a real failure. Use `60_000` timeouts on any test
that touches the model.

Do not change thresholds, `decide.ts`, or any RPC/migration.
