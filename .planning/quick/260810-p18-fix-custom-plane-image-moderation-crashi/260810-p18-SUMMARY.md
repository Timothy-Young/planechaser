# Summary — 260810-p18

Every custom plane submitted with art was being refused in production with
"That image could not be processed. Try a different file." The scan was
crashing, not flagging, and the catch that produced that message logged
nothing — so the cause had never been seen.

## The evidence

Supabase storage logs show four attempts on 2026-08-10 from one non-admin
user. In each, the route downloaded the pending object and deleted it again
0.15s to 0.5s later. One of the four was a PNG and the rest JPGs, all failing
identically, so no single file was at fault. The user's `profiles` row showed
`is_banned=false`, `nsfw_ack_required=false`, `custom_plane_cooldown_until=null`
— no verdict was ever reached and nothing hit the penalty ladder. The newest
row in `custom_planes` is 2026-07-10, i.e. nothing has been created since the
moderation route shipped.

Ruled out before touching code: the local pipeline is healthy
(`src/lib/moderation/image.test.ts` passes against the real model and real
sharp, no mocks); `next build` traces all three
`@tensorflow/tfjs-backend-wasm/dist/*.wasm` files and the nsfwjs mobilenet_v2
weights into `route.js.nft.json`; and bundling has not broken emscripten's Node
detection — the built chunk still contains the correct `ENVIRONMENT_IS_NODE`
expression.

## What shipped

- **`image.ts` — CPU fallback.** `tf.setBackend('wasm')` reports failure two
  ways (it rejects on some paths, resolves `false` on others). Both are now
  caught and fall through to `tf.setBackend('cpu')` with a logged warning. The
  measured cost is ~1750ms load plus ~1400ms classify versus ~330ms/~95ms on
  WASM with identical scores, and the route allows `maxDuration = 30`, so this
  is a slow success where the old code was a hard refusal. A CPU failure still
  propagates — nothing is ever published unscanned.
- **`image.ts` — non-poisoning model cache.** `modelPromise ??=` retained a
  rejected promise, so one failed cold start refused every later request that
  instance served. That matches four consecutive identical failures. The cache
  now clears on rejection, guarded by identity so a late handler from a
  superseded attempt cannot clobber a retry already in flight.
- **`types.ts` / `index.ts` — stage tagging.** `moderate()` ran both scans under
  one `Promise.all`, so a caller could not tell which half threw. A new
  `ModerationScanError` carries `stage` and the original error as `cause`. Both
  scans still run concurrently under one `Promise.all`. The class lives in
  `types.ts`, which imports no TensorFlow and no sharp, so importing it is free.
- **`route.ts` — logging and attribution.** The catch now logs unconditionally
  under `[custom-planes] moderation scan failed` (error object only; no fields,
  no image bytes). 400 `invalid_image` is returned only when
  `stage === 'image'`; a text-scan, a model-init crash, or any untagged error
  is a 500 `server_error`. Previously the mere presence of image bytes decided
  the message, which sent users off replacing art that was never the problem.

## Verified

`npm test` — 274 passed across 17 files, up from 272. `npm run typecheck` clean.
`npm run lint` 0 errors (56 pre-existing warnings, none in touched files).
`npm run build` succeeds and the route still traces 3 wasm binaries and 2 model
files.

New coverage: two tests in `image.test.ts` (a usable backend is selected;
a failed decode does not poison the next call), three in a new `index.test.ts`
(a real sharp decode failure tags `stage: 'image'` with a populated `cause`;
the text-only path cannot produce an image verdict or scores), and three in
`route.test.ts` (image stage → 400, text stage → 500, untagged → 500, each
still discarding the pending object and writing no strike). No mocked model
client was introduced anywhere.

The existing `route.test.ts` case that threw a bare `Error` and expected 400
was updated to throw the real `ModerationScanError`, since a bare error is now
correctly a server fault. It imports the real class rather than a stand-in —
the route branches on `instanceof`, so a fake would prove nothing.

## Migrations

None. This change touches no schema. The repo and hosted project are in sync
through `033_session_game_config`, confirmed both from the applied-migration
ledger and by querying for the objects themselves (`cards.border_color`,
`custom_planes.is_public`, `profiles.nsfw_ack_required`,
`set_nsfw_ack_required`, `record_nsfw_violation` — all present). The
`025_server_side_achievements` drift recorded earlier is resolved.

## Not verified

The root cause of the production crash is still unknown. Nothing here diagnoses
it — the point is that the next occurrence is no longer silent. After deploy,
submitting a plane with art gives one of two answers, and both end the
investigation:

- The plane saves. The CPU fallback or the cache reset was the fix.
- It fails again, and `[custom-planes] moderation scan failed` names the real
  error in the Vercel log for the first time.

No route-level integration test against a live Supabase was added; exercising
the handler needs a client double, and this project has been burned by mocked
tests that could not catch real failures.
